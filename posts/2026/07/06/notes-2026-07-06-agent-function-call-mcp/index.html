Agent 笔记：Function Call、MCP 和五种模式

Function Call 解决「模型如何提出一次调用」；MCP 解决「工具如何描述自己」；Agent 模式决定要不要规划、反思和协作。

#Agent #MCP #工具调用

把能调工具的对话系统直接叫 Agent，会把三件不同的事混在一起。课堂里的 SmartVoyage 旅行助手把它们拆开了：先有函数调用，再有 MCP 描述工具，再用不同 Agent 模式决定怎么用这些工具，A2A 则是多个智能体之间怎么说话。

Function Call：模型输出的是参数，不是散文

模型如果只回自然语言，应用就只能靠正则去「猜」它想查天气还是想订票。Function Call 把约定改成：模型在需要时输出符合 schema 的 JSON，由程序真正执行函数，再把结果还回模型。

三种常见写法：

  • 自己声明 tool 结构
  • 用装饰器把函数注册成 tool
  • 用 Pydantic 定义参数模型，少一次手工对字段

关键不在语法糖，而在：工具描述是否让模型知道「什么时候不该调」、参数校验失败怎么办、同一工具连调三次要不要熔断。

MCP：工具应该描述自己

每个应用开发者都按自己的理解写一遍工具说明，质量一定漂。MCP 的假设是：工具作者最清楚输入输出和副作用，应该由工具侧提供标准描述，模型应用去发现和调用。传输可以走 stdio、SSE 或 streamable，本质是「模型和外部系统之间的那根管子要标准化」。

对应用开发者，这意味着：少在业务仓库里维护一份容易过期的工具说明书，多把时间花在权限、超时和审计上。

Agent 不等于 Agentic

Agent 是一个能感知、决策、行动的实体。Agentic 描述的是自主程度。一个只调一次检索的问答，Agentic 很低，但可能正是正确的产品形态。

五种模式可以看成能力逐渐加码：

  1. Tool use：按需调一次或几次工具
  2. ReAct：边想边做，观察后再决定下一步
  3. Reflection：对已有结果做检查和修正
  4. Planning：先拆任务再执行
  5. Multi-agent：不同角色分工，例如「解析意图的人」和「去查票的人」

演进不是升级路径。能用 workflow 写死的顺序，就不要做成自由规划。工具有副作用时，Reflection 和步数上限比再加一个子 Agent 更重要。

A2A：智能体之间的协议

当天气、票务、行程规划不再塞在一个进程里，就需要一种方式让 Agent 发现对方、提交任务、拿回结果。A2A 管的是 Agent 与 Agent；MCP 管的是 Agent 与工具。两者叠在一起，才是「分布式助手」而不是「一个 prompt 里写了三个角色」。

调试时先看调用，再怪模型

把每一轮的 thought / tool / observation 落盘。先确认：

  • 模型有没有选对工具
  • 参数过没过 schema
  • 工具返回是不是被截断
  • 是否在同一个工具上打转

旅行助手这类项目适合当协议练习。真正接到业务时，还要补上权限、费用、审计，以及「查不到就停」的规则。
